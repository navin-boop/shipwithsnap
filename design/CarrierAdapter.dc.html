EasyPost integration
One provider does rates, labels, tracking, address verification and refunds. Product code talks to a thin ShippingProvider seam, never to EasyPost directly — so a second provider or a direct carrier account later is one new module.

// packages/shipping/provider.ts — one implementation today: EasyPostProvider interface ShippingProvider { // Creates the provider shipment and returns every rate on it. // `reference` = our shipment id, stored on the EasyPost Shipment. rate(req: RateRequest): Promise<{ providerShipmentId: string; rates: RateQuote[] }>; // Buys one rate. Idempotent: if the provider shipment already has a // postage_label, returns it instead of buying twice. buy(req: { providerShipmentId: string; providerRateId: string; insuranceCents?: number; format: LabelFormat }): Promise<LabelResult>; // Requests a refund; resolves with the provider's refund status. void(providerShipmentId: string): Promise<"submitted" | "refunded" | "rejected">; // Pull path for stale trackers. track(providerTrackerId: string): Promise<TrackingEvent[]>; // Push path. Verifies HMAC, returns [] when the event is not tracking. parseWebhook(raw: Buffer, headers: Headers): { eventId: string; events: TrackingEvent[] }; verifyAddress(a: Address): Promise<AddressValidation>; } type RateQuote = { providerRateId: string; // rate_… carrier: "USPS" | "UPS"; service: string; // GroundAdvantage, Ground… priceCents: number; // EasyPost `rate` — what we are billed retailCents: number | null; // EasyPost `retail_rate` — the strike-through estDays: number | null; estDelivery: string | null; }; type LabelResult = { providerLabelId: string; providerTrackerId: string; trackingCode: string; labelUrl: string; // fetched once, stored in our bucket chargedCents: number; }; type TrackingEvent = { dedupeKey: string; // sha1(status + datetime + message + city) — details carry no id status: CanonicalStatus; rawStatus: string; description: string; location?: { city?: string; state?: string; zip?: string }; occurredAt: string; };
Concern
How EasyPost covers it
Our side
Auth & environments
Production and test API keys · test keys buy free labels with fake tracking
Our sk_test_ keys route to the EasyPost test key; never mix per request
Carrier accounts
EasyPost-provided USPS and UPS accounts carry the discounted rates; customers may add their own ca_… accounts
carrier_accounts table holds optional customer ca_ ids; passed as carrier_accounts[] on rating
Rates
POST /v2/shipments returns rates[] with rate, retail_rate, list_rate, delivery_days, est_delivery_date
Rates live on the shipment, so a re-rate = new EasyPost shipment. Cache by (from, to, parcel) for 10 min
Labels
POST /v2/shipments/{id}/buy with rate.id, optional insurance · postage_label.label_url · PNG default, PDF / ZPL via label_format or POST …/label
Download once, store in our bucket, serve signed URLs. Never link customers to EasyPost URLs
Void / refund
POST /v2/shipments/{id}/refund → refund_status: submitted → refunded | rejected (USPS async, UPS fast)
Stripe refund to the card on refunded; show "refund pending" while submitted; poll daily up to 30 d
Tracking
A Tracker is created with every buy · tracker.updated webhooks, HMAC-signed · GET /v2/trackers/{id} to pull
Dedupe webhook by event.id; dedupe details by hash. Poll only trackers silent > 24 h
Addresses
POST /v2/addresses with verify[]=delivery · returns corrected address, residential, and verification errors
Cache by hash; surface the corrected form for one-click accept
Batch
EasyPost Batch can buy N shipments and produce one merged label file
We loop our own buys for per-row control and use Batch.label only for the merged PDF
Billing
Postage is charged to Snap's EasyPost account (prefunded balance or invoice) · carrier adjustments post to the shipment as fees
Customers pay per purchase on Stripe (see 6). Nightly job pulls EasyPost fees → adjustment charges
Retries & idempotency
No idempotency-key header on buy. Shipment reference field is ours to set
On timeout, GET /v2/shipments/{id} and check postage_label before ever calling buy again
Contract tests run the provider against recorded EasyPost fixtures in CI and against the test API nightly — rate, buy, void, track, parseWebhook, verifyAddress — so an EasyPost change fails a build, not a customer.
Circuit breaker: 5 failures in 60 s trips it; the Ship page shows "rates are temporarily unavailable" with a retry, and no hold is ever placed while it's open.
